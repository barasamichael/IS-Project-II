# How to read this document

Each milestone represents a self-contained unit of work that must be completed before the next milestone begins. Every milestone maps directly to findings in FEEDBACK.md and standards in SB-TECH-2026-001. Milestones are ordered by dependency and urgency. A milestone is complete only when every condition in its completion criteria is met and verified.

# Milestone 1 — Immediate Security and Safety

**Purpose:** Remove every issue that makes the system unsafe or unfit for any user contact. Six findings are P0 — they can cause immediate harm or system compromise today, with the live codebase as it stands. Two of them are single-line fixes. All six must be resolved before any other work proceeds and before the system is shown to any external person.

**Completion criteria:** No `print()` call exists anywhere in `api/`, `services/`, `config/`, or `utilities/`. The API key is not stored in `config/config.yaml`. The file upload endpoint rejects filenames containing path separators. The system prompt produced by `_get_comprehensive_system_prompt()` contains the grounding rule as its first instruction block before all other content. `evaluator.py` calls `get_intent_info()` and not `recognize_intent()`. The duplicate language detection call at `api/main.py:578–589` is removed. SSL verification is enabled in `config/config.yaml` and no MITM vulnerability exists on URL ingestion. `debug` is set to `false` in `config/config.yaml`. Tavily web content is sanitised through `sanitise_web_content()` before being inserted into the LLM context. All items in the P0 and security-related P1 rows of the FEEDBACK.md action plan are closed.

The `api/main.py:645` `print(query_response)` call must be deleted entirely — it dumps a full Pydantic model including up to 15 retrieved document chunks to stdout on every request. This is not to be converted to a log statement; it is to be removed. The six other `print()` statements at `api/main.py:575`, `api/main.py:620`, `language_processor.py:170`, `intent_recognizer.py:766`, `response_generator.py:397`, and `response_generator.py:1109` are each to be replaced with structured `logger.info()` or `logger.debug()` calls carrying the same information as key-value pairs using `structlog`. No `print()` call may remain in any file under `api/`, `services/`, `config/`, or `utilities/` after this milestone is complete.

The API key at `config/config.yaml` line 122 is the literal string `"your_secure_random_key_here"`. This value is committed to version control and is publicly known to anyone who has cloned this repository. The `api_key` field must be removed from `config/config.yaml` entirely. It must be moved to an environment variable `SETTLEBOT_API_KEY` read by `config/settings.py` using `os.getenv()`. The `.env.example` file must include this variable. Any deployment that does not set this variable must fail to start, not start with an insecure default.

The file upload endpoint at `api/main.py:799` constructs `temp_file_path = UPLOAD_DIR / file.filename`. A filename containing `../../` would escape the uploads directory entirely. This must be fixed by extracting only the basename: `safe_name = Path(file.filename).name`. The endpoint must then reject any filename where `Path(file.filename).name != file.filename` (i.e., any filename that contained path components).

The evaluator at `evaluator.py` lines 466 and 1352 calls `self.intent_recognizer.recognize_intent(query)`. This method does not exist. The correct method is `get_intent_info(query)`. This must be corrected at both call sites. This is a one-line fix per location and unblocks the entire evaluation pipeline which has never successfully run.

The grounding rule must be added to `_get_comprehensive_system_prompt()` in `response_generator.py` as the very first block of every system prompt before any intent-specific or locale-specific content. The rule text is specified in SB-TECH-2026-001 Section 3.2.12 and must be reproduced verbatim. The three prompt instructions that currently tell the LLM to "Include specific contact numbers" and "Provide specific contacts, websites, and resources" must be removed or replaced with language that refers only to contact details already present in the retrieved context. The grounding rule alone does not eliminate hallucination risk permanently — that is addressed in Milestone 4 — but it immediately constrains the LLM's current instruction to fabricate.

The duplicate language detection call at `api/main.py:578–589` must be deleted. `language_processor.detect_and_process_query()` is already called inside `response_generator.generate_response()` at line 660. The block at `api/main.py:578–589` that also calls it is the duplicate. Removing it eliminates one full gpt-4.1-nano LLM call per query, reducing latency by 1–2 seconds and halving language detection costs.

`config/config.yaml` line 36–37 sets `ssl: enable_verification: false`. This disables SSL certificate verification for all `WebBaseLoader` calls in `document_processor.py:796`, enabling man-in-the-middle attacks when fetching content from external URLs during document ingestion. This must be set to `true`. If any specific URL ingestion target requires certificate handling, it must be addressed explicitly rather than by disabling verification globally.

`config/config.yaml` line 123 sets `debug: true`. In debug mode, `internal_error_handler` at `api/main.py:2269` returns `str(exc)` in every 500 error response, leaking internal file paths, library versions, and data to API consumers. This must be set to `false`. The `debug` and `api_key` fields must ultimately be read from environment variables so that no security-sensitive configuration is ever committed to version control.

The `utilities/sanitisation.py` module must be created with a `sanitise_web_content(text: str) -> str` function. This function must detect prompt injection patterns using a regex against phrases like `"ignore all previous instructions"`, `"disregard the above"`, and similar variants (case-insensitive). If a match is found, it must return a safe replacement string rather than the raw content. It must also hard-cap content length at 1500 characters. The call in `response_generator.py` lines 967–972 that currently appends `result["content"]` verbatim into the LLM context must be replaced with a call to `sanitise_web_content(result["content"])`.

# Milestone 2 — Production Hardening and Observability

**Purpose:** Transform the system from a working prototype into a production-grade service. Milestone 1 removed immediate safety risks. This milestone adds the operational infrastructure required to run the system reliably: structured logging, request tracing, rate limiting, input validation, resilient LLM call handling, and accurate system status reporting. None of these changes alter business logic. All are infrastructure concerns that must be in place before the system handles real user load.

**Completion criteria:** All seven remaining `print()` calls identified in Milestone 1 are replaced (those not already removed in Milestone 1 were `api/main.py:575`, `api/main.py:620`, `language_processor.py:170`, `intent_recognizer.py:766`, `response_generator.py:397`, `response_generator.py:1109`). Structlog is configured with a JSON renderer and initialised at startup. Every request carries a correlation ID in `X-Request-ID`. The `/query` endpoint enforces a rate limit of 30 requests per minute per IP. `QueryRequest.query` enforces `min_length=3, max_length=2000`. All LLM calls in `language_processor.py` and `response_generator.py` are wrapped with tenacity retry logic and an explicit 15-second timeout. Tavily calls carry a 4-second explicit timeout. The four stub endpoints are corrected. `uptime_hours` reports a real value. The `googletrans` dependency is removed from `requirements.txt`. LangChain package versions are pinned to a single compatible release set.

Structlog must be configured once at startup in `app.py` using the JSON renderer, the `contextvars` processor, a log level processor, a logger name processor, and an ISO timestamp processor. This replaces the `logging.basicConfig(level=logging.INFO)` calls scattered across every service file. Each service file retains its `logger = logging.getLogger(...)` but all output now flows through structlog's pipeline to structured JSON. Every log entry for a request must carry the `request_id` field, which is injected via `structlog.contextvars.bind_contextvars(request_id=request_id)` in the correlation ID middleware.

The correlation ID middleware must be added to `api/main.py`. If an incoming request carries an `X-Request-ID` header, that value is used. Otherwise a UUID4 is generated. The ID is bound to the structlog context for the duration of the request and returned in the `X-Request-ID` response header. This makes every request traceable end-to-end in logs, resolving the current situation where a specific user complaint cannot be investigated in any log.

Rate limiting must be added using `slowapi`. The `Limiter` must use `get_remote_address` as the key function. The `/query` endpoint must be decorated with `@limiter.limit("30/minute")`. The `/documents/upload` endpoint must be decorated with `@limiter.limit("10/minute")`. A handler must be registered for `RateLimitExceeded` that returns a structured error response matching the project's standard error format rather than a bare HTTP 429.

`QueryRequest` must declare `query: str = Field(..., min_length=3, max_length=2000)`. Pydantic will reject queries outside this range before any service code executes. Without this, a single 50,000-character query reaches the OpenAI embedding API and the LLM, causing API errors and potentially significant cost.

Every LLM call in `language_processor._detect_and_translate_llm()` (line 156) and `response_generator._generate_comprehensive_response()` (line 1099) must be wrapped using tenacity as specified in SB-TECH-2026-001 Section 3.2.11. The retry policy must use three attempts with exponential backoff (minimum 1 second, maximum 8 seconds) and retry only on `openai.RateLimitError` and `openai.APITimeoutError`. Each call must include `timeout=15` in the `chat.completions.create()` call. Currently these methods have no timeout and no retry, meaning a single OpenAI API slowdown silently stalls the entire request until the OS connection timeout fires.

The Tavily `search_web_for_current_info()` call in `response_generator.py` line 389 must add `timeout=4` to the `tavily_client.search()` call. The existing `TimeoutError` and general exception handling already in the surrounding `try/except` block will handle the timeout gracefully by returning `None`, which causes the system to proceed with RAG-only results as it does when the API key is absent.

The four stub endpoints must be corrected. `GET /analytics/search-patterns` must return HTTP 501 with `{"status": "not_implemented", "message": "Search pattern analytics require query logging infrastructure not yet implemented."}` — it must not pretend to return analytics it does not have. `uptime_hours` in the system status response must be replaced with a real computation: store `startup_time = datetime.now()` in the `startup_event()` handler and compute `uptime_hours = (datetime.now() - startup_time).total_seconds() / 3600` in the status endpoint. `POST /vector-db/optimize` currently returns `"status": "optimized"` and does nothing; it must return `"status": "no_op"` with a list of `"optimizations_available"` describing the BM25 and cross-encoder upgrades planned for Milestone 7. The webhook callback at `api/main.py:2223–2226` that claims to send an HTTP POST but only sets `callback_sent=True` in a dict must either be implemented using `httpx.AsyncClient` or changed to return HTTP 501.

The `avg_quality_score` field in `EmbeddingService.validate_embeddings_quality()` at `embeddings.py:641` that always returns `0.8` as a placeholder must be removed from the public stats returned by the `/embeddings/stats` endpoint. A hardcoded quality score is misleading; the field should be omitted until real quality measurement is implemented.

The `googletrans==4.0.2` package must be removed from `requirements.txt`. `LanguageProcessor` does not import or use it despite it appearing as a dependency. The config setting `translation_provider: hybrid_gpt_google` is misleading — the implementation is OpenAI-only. This setting must either be corrected to `translation_provider: openai` or removed, and the `LanguageConfig` Pydantic model updated accordingly.

LangChain package versions in `requirements.txt` must be reviewed to ensure `langchain`, `langchain-community`, `langchain-core`, `langchain-openai`, and `langchain-text-splitters` are pinned to a single compatible release set. The current `requirements.txt` lists `langchain==1.0.7`, `langchain-community==0.4.1`, and `langchain-core==1.0.5` — these must be verified as mutually compatible and pinned together. Any breaking changes introduced by the pinned versions must be resolved before this milestone closes.

# Milestone 3 — Request Pipeline Latency Reduction

**Purpose:** Reduce end-to-end query latency from the measured 47+ second baseline to under 15 seconds without degrading response quality. The latency problems are structural: redundant API calls, sequential operations that could be parallel, and the absence of any caching. This milestone redesigns the request pipeline following the target architecture described in FEEDBACK.md Phase 1 Proposed Fix.

**Completion criteria:** End-to-end latency measured from `/query` request to response is consistently under 15 seconds for typical queries with Tavily enabled and under 10 seconds with Tavily disabled. Only one embedding model is called per query. Only one language detection call occurs per query (the one already inside `response_generator.generate_response()`). Vector search and Tavily search execute in parallel rather than sequentially. Query embeddings are cached with an in-process LRU. Tavily results are cached with a TTL. `max_tokens` is capped at 2048 for non-emergency intents. ChromaDB calls from async endpoint handlers are wrapped with `asyncio.to_thread()`. The intent recognizer uses `settings.embedding.model` and not the hardcoded `"text-embedding-ada-002"`.

The embedding model used by `IntentRecognizer` must be unified with the model used by `EmbeddingService`. Currently `intent_recognizer.py` lines 675 and 765 hardcode `"text-embedding-ada-002"` while `EmbeddingService` reads `settings.embedding.model` which is `"text-embedding-3-small"`. These are different vector spaces, meaning two separate embedding API calls are made per query using two different models. `intent_recognizer.py` must replace both hardcoded model strings with `settings.embedding.model`. After this change, the intent embedding cache at `.embeddings_cache/intent_embeddings.npz` is invalidated and must be rebuilt by calling `intent_recognizer.rebuild_cache()`. The cache metadata at `.embeddings_cache/intent_metadata.json` must store the model name so that future model changes automatically invalidate the cache.

Query embeddings must be cached using `functools.lru_cache(maxsize=512)` on `EmbeddingService.embed_query()`. The cache key is the normalised query string (lowercased, whitespace-normalised). Since embeddings are deterministic for a given model and input, no TTL is needed. This eliminates repeat embedding API calls for the same query — common in interactive or demo sessions where the same questions recur. The shared embedding vector must then be passed to both the intent recognizer and the vector database search so that neither generates a second embedding for the same query.

The request flow in `api/main.py` and `response_generator.generate_response()` must be restructured so that vector DB search and Tavily search execute in parallel after intent classification, not sequentially. Specifically: after the intent type is determined, both `vector_db_service.search()` and `search_web_for_current_info()` must be submitted to a `ThreadPoolExecutor` (or rewritten as `asyncio.to_thread()` calls) simultaneously. The current code starts Tavily inside the `ThreadPoolExecutor` but only after the vector DB search has already completed sequentially. The restructuring must submit both to the executor at the same time and collect their results together before assembling the context.

ChromaDB's Python client is synchronous. `VectorDBService.search()` calls `self.collection.query()` which blocks the async event loop when called from a FastAPI route handler. All ChromaDB calls made from within async FastAPI route handlers or async service methods must be wrapped with `await asyncio.to_thread(self.collection.query, ...)`. This allows the event loop to handle other requests while ChromaDB operations are running.

Tavily results must be cached using `cachetools.TTLCache(maxsize=200, ttl=3600)`. The cache key is `(intent_type.value, normalised_query[:100])`. Any query with `crisis_level == "high"` must bypass this cache because emergency information must always be freshly retrieved. The cache must be initialised once at module load time and shared across requests in the same process.

The `max_tokens` parameter for response generation must be reduced from 4096 to 2048 for all intents except `EMERGENCY_HELP` (which retains 4096 to ensure complete emergency guidance is never truncated). The current 4096 setting is the primary driver of response latency because the LLM generates tokens until it reaches the limit. Practical response quality in tests shows responses are complete well within 2048 tokens for typical settlement queries. This single change is expected to reduce the response generation step from 4–10 seconds to 2–5 seconds.

Both constants (`LLM_RESPONSE_MAX_TOKENS = 2048` and `LLM_EMERGENCY_MAX_TOKENS = 4096`) must be defined in `config/constants.py` and read from there by `response_generator.py`. The current hardcoded `max_tokens=self.max_tokens` from `settings.llm.max_tokens` must be replaced with the intent-aware selection.

*References: FEEDBACK.md Phase 1 (all findings and proposed fix), Phase 8 (token budget), SB-TECH-2026-001 §3.2.8, §3.2.13*

# Milestone 4 — Factual Grounding and Hallucination Prevention

**Purpose:** Prevent the LLM from fabricating phone numbers, addresses, and institutional details. The audit confirmed fabricated numbers in live responses including `+254 700 000 000` (a placeholder), `+254 (0) 20 2100272`, and `0709 123 456` — three different invented numbers for the same immigration office. The grounding rule added in Milestone 1 was a quick constraint. This milestone builds the structural mechanisms that make grounding systematic and verifiable rather than dependent on LLM instruction-following.

**Completion criteria:** The `essential_info` dictionary in `response_generator.py` lines 44–261 no longer contains hardcoded contact information. Fact data is loaded at startup from a JSON file per locale in `config/locale/`. A `LocaleFactStore` class reads the JSON and exposes the data to the response generator. A `utilities/factcheck.py` module provides `extract_phones_from_context()` and `normalise_phone()` functions. A post-generation audit runs on every response before it is returned, flags unverified phone numbers, and replaces them with a safe fallback string. Every retrieved chunk contributes its `doc_id` and `chunk_id` to the LLM context as an inline citation label. Every response includes a `## SOURCES` section listing the document IDs that contributed to the answer. The evaluator test set contains at least five phone-number correctness checks. A `/admin/update-facts` endpoint allows operators to update the fact store for a locale without a code deploy.

The `essential_info` dictionary in `response_generator.py` that hardcodes 14 hospitals, 16 universities, immigration office details, and 6 emergency numbers must be extracted into a JSON file at `config/locale/nairobi.json`. This file is the canonical fact store for the Nairobi deployment. A `LocaleFactStore` class must be created in `config/locale.py` that loads this file at startup, validates its structure against a Pydantic schema, and exposes typed accessors. `ResponseGenerator.__init__` must accept a `fact_store: LocaleFactStore` parameter and use it in place of `self.essential_info`. The fact store JSON schema must define required fields for emergency contacts, hospitals, universities, government offices, and transport operators, each entry carrying a `verified_date` field and an `official_source_url` field so operators know when data was last checked and where to verify it.

The `utilities/factcheck.py` module must implement `extract_phones_from_context(context_text: str, fact_store: LocaleFactStore) -> set[str]` which returns the set of all verified phone numbers present in the fact store and in the retrieved chunk texts. It must implement `normalise_phone(phone: str) -> str` which strips spaces, hyphens, and leading zeros to produce a canonical comparison form. After `_generate_comprehensive_response()` returns and before the response is returned from `generate_response()`, `PHONE_RE = re.compile(r'(\+254[\s\-]?\d[\d\s\-]{7,}|\b0[17]\d{2}[\s\-]?\d{3}[\s\-]?\d{3}\b)')` must be applied to the response text. Any matched phone number that does not appear in `extract_phones_from_context()` must be replaced with `[contact details unavailable — verify at official source]`. This step catches hallucinations that slip through the grounding rule.

The LLM context assembled in `_format_comprehensive_context()` must label each retrieved chunk with its source. The current format appends raw chunk text under `Source N (Relevance: X.XX):`. This must be extended to `Source N (doc_id: {chunk["doc_id"]}, chunk: {chunk["chunk_id"]}, relevance: {score:.2f}):`. The system prompt must be updated to instruct the LLM to cite source numbers when making factual claims. A `## SOURCES` section must be appended to every response containing the list of `doc_id` values that were used. This allows operators to trace any response back to a specific document in the knowledge base.

The three response generation prompt lines that instructed hallucination — "Include specific Nairobi details - locations, costs in KSh, contact numbers", "Include specific contacts, websites, and resources", and "Provide specific contacts, websites, and locations" — must be replaced with language that reads: "Include only specific details, costs, and contact information that appear verbatim in the RETRIEVED SETTLEMENT INFORMATION or ESSENTIAL SETTLEMENT INFORMATION sections provided. If a detail is not in the provided context, do not include it."

A `/admin/update-facts` endpoint must be implemented that accepts a JSON payload matching the `LocaleFactStore` schema, validates it against the schema, writes it to the appropriate locale JSON file, and reloads the `LocaleFactStore` in memory without requiring a server restart. This endpoint must require API key authentication and write an audit log entry each time it is used.

The `create_international_student_eval_set()` method in `evaluator.py` must add phone number correctness checks to the evaluation set. For each question whose reference response contains a phone number, the evaluation must extract all phone numbers from the generated response and verify each against the fact store. Any unverified number is a failed test. This check must be distinct from the BLEU score and keyword presence checks, and must be reported separately in the evaluation report as `phone_hallucination_rate`.

*References: FEEDBACK.md Phase 2 (all findings and proposed fix), Phase 5 (evaluator), SB-TECH-2026-001 §3.2.12, §3.3, §3.4.2*

# Milestone 5 — Web Search Robustness

**Purpose:** Make Tavily integration production-safe. Currently the system calls Tavily on every query regardless of whether fresh web data is needed, accepts any web result without quality filtering, and has no protection against the web content overriding authoritative knowledge-base data. This milestone implements intent-based routing, source quality filtering, priority ordering, and cost reduction through selective invocation.

**Completion criteria:** Tavily is called only for the intents where freshness matters: always for `IMMIGRATION_VISA` and `COST_INQUIRY`, conditionally for `HOUSING_INQUIRY` and `BANKING_FINANCE` when RAG retrieval confidence is below 0.5, and never for `CULTURAL_ADAPTATION` or `EMERGENCY_HELP`. Each locale JSON file defines a `trusted_domains` list. Tavily results are filtered to retain only those from trusted domains. Results from untrusted domains are discarded. Retrieved RAG chunks are presented in the LLM context before web results, with an explicit label indicating which is authoritative knowledge-base content and which is supplementary web content. The `sanitise_web_content()` function implemented in Milestone 1 is called on every web result before context assembly. A Tavily result cache with TTL=3600 is active and shared across requests. Tavily timeout is confirmed at 4 seconds.

The `search_web_for_current_info()` method in `response_generator.py` must be preceded by an intent-based routing check. The routing rules are: `IMMIGRATION_VISA` and `COST_INQUIRY` always trigger a web search because visa fees, permit requirements, and living costs change frequently and the knowledge base may be stale. `HOUSING_INQUIRY` and `BANKING_FINANCE` trigger a web search only when the top retrieved chunk has a relevance score below 0.5, indicating the knowledge base has insufficient coverage for this query. `SAFETY_CONCERN`, `TRANSPORTATION`, `HEALTHCARE`, `UNIVERSITY_INFO`, and `PROCEDURAL_QUERY` follow the same conditional logic as housing. `CULTURAL_ADAPTATION` never triggers a web search — cultural information is stable and the knowledge base is the appropriate source. `EMERGENCY_HELP` never triggers a web search — emergency responses must come from the verified `LocaleFactStore` only, not from web results that could be inaccurate.

The `LocaleConfig` data structure introduced in Milestone 8 carries a `trusted_domains: list[str]` field populated in the locale JSON file. For the Nairobi locale this list includes `immigration.go.ke`, `ecitizen.go.ke`, `centralbank.go.ke`, `safaricom.co.ke`, `knh.or.ke`, `uonbi.ac.ke`, `strathmore.edu`, and other verified government and institutional domains. After Tavily returns results, they must be filtered: `results = [r for r in results if any(d in r.get("url", "") for d in locale.trusted_domains)]`. If no results survive the filter, the web search path returns `None` and the response generation continues with RAG-only context, exactly as it does when Tavily is unavailable. This must not raise an error or degrade response quality — it is a normal fallback path.

The context assembly in `_format_comprehensive_context()` must clearly distinguish knowledge-base content from web content in the string passed to the LLM. RAG chunks must appear first under the header `KNOWLEDGE BASE — AUTHORITATIVE CONTENT:` and web results must appear second under `WEB SUPPLEMENT — VERIFY BEFORE CITING:`. The system prompt must instruct the LLM to prefer knowledge-base content over web content when both address the same topic, and to treat web content as supplementary. Currently both sources are concatenated without any priority signal, which causes web results to dominate in practice because they appear more authoritative in the LLM's context.

The Tavily result cache introduced in Milestone 3 (`cachetools.TTLCache(maxsize=200, ttl=3600)`) is the same cache used here. No duplicate implementation is needed. This milestone confirms it is active and that the cache bypass for `crisis_level == "high"` queries is implemented.

*References: FEEDBACK.md Phase 4 (all findings and proposed fix), SB-TECH-2026-001 §3.3*

# Milestone 6 — Intent Recognition Accuracy

**Purpose:** Fix the intent classification system so that it correctly identifies what a user is asking and does not return authoritative settlement responses for off-topic queries. The adversarial test results in FEEDBACK.md Phase 5 show specific failure cases: `"What is bread?"` received a full settlement response, `"Where can I find halal food?"` was classified as `university_info`, and the evaluator test set references seven intent types that do not exist in `IntentType` enum. The evaluator itself has never successfully run.

**Completion criteria:** The evaluator runs to completion without any `AttributeError`. All `expected_intent` values in the evaluation CSV match values in `IntentType` enum. Adversarial queries including `"What is bread?"` and `"Where can I find injera near Westlands?"` are classified as `OFF_TOPIC` and return the standard off-topic response. The classification for `"Where can I find halal/kosher/vegetarian food?"` is `cultural_adaptation` rather than `university_info`. Per-intent confidence thresholds are stored in `config/constants.py`. Ambiguous queries where the top two intent scores differ by less than 0.05 trigger a clarification response. When cosine similarity falls between 0.40 and 0.55 for all intents, a gpt-4.1-nano fallback classifier is called and its result is used.

The `expected_intent` values in the `eval_questions` list inside `create_international_student_eval_set()` that use undeclared types must be corrected to use values from `IntentType` enum. The mapping is: `reassurance_seeking` → `safety_concern`, `comparison_query` → the applicable domain intent (e.g., `banking_finance` for bank comparison questions, `university_info` for university comparison questions), `explanation_query` → `banking_finance` or `transportation` depending on the topic, `entertainment_social` → `cultural_adaptation`, `shopping_markets` → `cultural_adaptation`, `academic_conversion` → `university_info`, `neighborhood_guide` → `housing_inquiry`. These corrections make the evaluator's intent accuracy metric meaningful rather than always failing for these test cases.

Per-intent confidence thresholds must replace the single global `off_topic_threshold = 0.40`. A `INTENT_THRESHOLDS: dict[IntentType, float]` constant must be added to `config/constants.py` with a starting value of `0.40` for all intents. Once the evaluator is running, these values must be tuned empirically: for each intent, the threshold must be set to the minimum cosine similarity score at which the intent achieves precision ≥ 0.90 on the evaluation set. Until empirical tuning is complete, the defaults of `0.40` are acceptable but the infrastructure to support per-intent thresholds must be in place.

Multi-label scoring must be implemented in `IntentRecognizer.classify_intent()`. After calculating cosine similarities, the method must identify whether the top two scores are within 0.05 of each other. If they are, `IntentResult` must carry an `is_ambiguous: bool = True` flag and a `secondary_intent: Optional[IntentType]` field. This information must be passed through to `generate_response()` which must, for ambiguous queries, return a clarification prompt: `"Are you asking about [intent_A topic] or [intent_B topic]? Please choose or rephrase."` The ambiguity state must be stored in `conversation_context` so the follow-up query is interpreted correctly.

An LLM fallback classifier must be added to `classify_intent()` for cases where all cosine similarities fall between 0.40 and 0.55. In this range, the semantic similarity is too low for confident classification but not low enough to confidently call off-topic. The fallback makes a single `gpt-4.1-nano` call with a few-shot prompt containing one representative example from each of the 11 intent types and asks the model to classify the query. The result overrides the cosine-based classification. This path fires for fewer than 10% of queries in practice and adds approximately 1 second of latency only when triggered.

The intent prototype embeddings in `.embeddings_cache/` were built using `text-embedding-ada-002`. After the embedding model is unified to `settings.embedding.model` in Milestone 3, this cache is invalid. The cache metadata at `.embeddings_cache/intent_metadata.json` must be updated to store the model name, and the cache validation logic in `_cache_is_valid()` must include a model name check. If the stored model name differs from `settings.embedding.model`, the cache must be invalidated and rebuilt automatically rather than requiring a manual `rebuild_cache()` call.

# Milestone 7 — Document Ingestion and Retrieval Upgrade

**Purpose:** Fix document ingestion so it is practical to use at scale, and upgrade retrieval accuracy to current best practice. Currently ingesting a single 20-chunk document costs 21 LLM API calls, making bulk ingestion prohibitively slow and expensive. Deduplication is configured but never runs. The retrieval pipeline is purely dense, which misses results for exact-phrase queries. BM25 sparse retrieval with Reciprocal Rank Fusion and a cross-encoder reranker would bring retrieval accuracy to the current industry standard for RAG systems.

**Completion criteria:** Processing a document through the ingestion pipeline makes at most 1 LLM call regardless of how many chunks the document produces. The `enable_deduplication=True` flag causes actual deduplication to occur: new chunks are compared against existing ChromaDB embeddings and near-duplicates are skipped. The `ChunkingStrategy` enum includes a value that matches the string `"semantic"` in `config/config.yaml`, and the chunker is instantiated using the config value rather than the hardcoded default. BM25 index is built from all stored documents and updated on ingestion. Query-time retrieval uses BM25 + dense fusion with Reciprocal Rank Fusion. A cross-encoder reranks the fused candidates before the final top-k are returned. Retrieved chunks pass their `doc_id` and `chunk_id` to the LLM context as inline citations (implemented in Milestone 4 but dependent on this milestone for the improved retrieval).

`SemanticChunker._enrich_chunks_with_llm_analysis()` must be refactored to eliminate per-chunk LLM calls. The `_analyze_chunk_with_llm()` method must be replaced with calls to `_calculate_settlement_relevance_score()` from `document_processor.py`, which computes the same settlement relevance score using deterministic keyword matching. This method already exists and already produces scores that are used in retrieval boosting. The one-per-document `_analyze_text_with_llm()` call in `_settlement_optimized_chunking()` is retained because it provides document-level routing information that keyword scoring cannot replicate. The net effect is that ingesting a 20-chunk document drops from 21 LLM calls to 1.

The config/chunker alignment bug must be resolved. `config/config.yaml` line 27 sets `strategy: semantic` but no `ChunkingStrategy` enum value matches `"semantic"`. Either add `SEMANTIC = "semantic"` to the `ChunkingStrategy` enum as an alias for `SETTLEMENT_OPTIMIZED`, or change `config.yaml` to `strategy: settlement_optimized`. Additionally, `api/main.py` must instantiate the chunker using the config value: `semantic_chunker = SemanticChunker(strategy=ChunkingStrategy(settings.chunking.strategy))`. Currently the chunker ignores the config entirely because it is instantiated with no arguments.

Deduplication must be implemented in `DocumentProcessor._create_settlement_chunks()`. After generating embeddings for a batch of new chunks, the method must search the existing ChromaDB collection for each chunk's embedding using a high `top_k` value (e.g. 5). Any new chunk whose nearest neighbour returns a cosine similarity ≥ `self.similarity_threshold` (currently 0.92) must be skipped — it is a near-duplicate of content already in the knowledge base. The `enable_deduplication` flag in `__init__` must actually gate this logic rather than being a no-op parameter.

BM25 hybrid retrieval must be added to `VectorDBService`. The `rank_bm25` package (`pip install rank-bm25`) provides `BM25Okapi` which is lightweight and requires no external service. On collection load and on every `index_chunks()` call, a BM25 index must be built from the stored document texts. At query time, `VectorDBService.search()` must retrieve `top_k * 2` candidates from the dense ChromaDB index and separately fetch `top_k` candidates from the BM25 index. These two ranked lists must be merged using Reciprocal Rank Fusion: `rrf_score(doc) = sum(1 / (k + rank_in_list_i) for each list_i)` where `k=60` is the standard smoothing constant. The merged list is sorted by RRF score and the top `top_k` candidates are passed to the reranker.

A cross-encoder reranker must be added using `sentence_transformers.CrossEncoder` with the `cross-encoder/ms-marco-MiniLM-L-6-v2` model, which runs locally with no API cost. After BM25+dense fusion produces the top `top_k * 2` candidates, the cross-encoder scores all `(query, chunk_text)` pairs and reranks them by score. Only the top `top_k` after reranking are returned. The cross-encoder must be initialised once as a class attribute on `VectorDBService` at startup and reused across requests — it must not be reinitialised per query.

The `_generate_settlement_queries()` method in `vector_db.py` line 626 that unconditionally appends `"in Nairobi Kenya"` to queries for multi-query expansion must be updated to use `locale.city` and `locale.country` from the `LocaleConfig` object introduced in Milestone 8. This dependency means the full locale refactor is in Milestone 8 but the `_generate_settlement_queries()` fix must be implemented in this milestone with a `locale` parameter passed to the method.

*References: FEEDBACK.md Phase 6 (all findings and proposed fix), SB-TECH-2026-001 §3.2.14, §3.4.3, §3.4.4*

# Milestone 10 — Frontend Chat Interface Completion

**Purpose:** Complete and stabilise the Flask web frontend so that users can interact with the RAG API through a working chat interface. The `front-end/app/templates/anonymous/chat.html` is under active development (git status shows it modified). This milestone defines the completion criteria for that work and adds the frontend infrastructure needed for a production-quality user experience.

**Completion criteria:** A user can submit a query through the chat interface and receive a response rendered with correct Markdown formatting. The three-section response structure (`## DIRECT ANSWER`, `## ADDITIONAL INFORMATION`, `## NEXT STEPS`) is rendered with clear visual hierarchy rather than as raw Markdown headers. The `## SOURCES` section added by Milestone 4 is rendered as a collapsible citation list, not as visible body text. The chat interface correctly displays the conversation history within a session. Error states (API key missing, rate limit hit, network error) display a user-facing message rather than crashing or showing raw JSON. The language detection indicator shows when the user's query was detected as non-English and when translation was applied. The frontend passes all Flask authentication tests from Milestone 9 Module 10. No hardcoded localhost URLs or development-only configuration values appear in the frontend templates or JavaScript.

The chat template at `front-end/app/templates/anonymous/chat.html` must submit queries to the RAG API endpoint and render responses. The API endpoint URL must be read from a Flask config variable `RAG_API_URL` set via environment variable — it must not be hardcoded as `http://localhost:8000` in the template. The `SETTLEBOT_API_KEY` used to authenticate with the RAG API must be read from the Flask environment config, not embedded in any template or JavaScript file.

Response text from the RAG API contains Markdown formatting. The frontend must render Markdown correctly. The three section headers `## DIRECT ANSWER`, `## ADDITIONAL INFORMATION`, and `## NEXT STEPS` must render as visually distinct section dividers, not as raw `##` strings. Bold text (`**text**`) must render as bold. Numbered and bulleted lists must render as HTML lists. The `## SOURCES` section must be rendered as a collapsed disclosure element (HTML `<details>/<summary>`) so it is accessible but does not dominate the visible response.

The chat session must persist conversation context within the browser session. Each submitted query must include the previous conversation history in the `conversation_context` field of the `QueryRequest` payload so the RAG API can use it for context-aware responses. On session end (browser close or explicit "Clear conversation" action), the history must be cleared. The language detection indicator must be displayed as a small badge on any response where the API returns `language_info.translation_needed = true`. The badge must show the detected language name. This signals to the user that their non-English query was understood and responded to in their language.

Error handling must cover at minimum: HTTP 429 (rate limit) displayed as "Too many requests — please wait a moment", HTTP 401 (authentication) displayed as "Service temporarily unavailable", HTTP 422 (validation — query too short/long) displayed as "Please enter a question between 3 and 2000 characters", and network errors displayed as "Could not reach the assistant — please check your connection." None of these must show raw API error JSON to the user.

The Flask app's `config.py` hardcodes `SECRET_KEY` with a development fallback. For the frontend to be deployable, this key must be set via environment variable in production. The `config.py` pattern of `os.environ.get("SECRET_KEY") or "E6GlTc..."` is acceptable for development but the fallback must be replaced with a startup assertion that fails loudly if `SECRET_KEY` is not set when `FLASK_ENV=production`.
